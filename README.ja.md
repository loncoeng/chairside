# chairside

*[English version](README.md)*

マカオの美容室向けの予約・顧客管理システムです。セット面9台、シャンプー台3台、
そして MOP・HKD・CNY の3通貨。実在の1軒を想定して作りました。

置き換える相手は、マクロを少し足した Excel です。

**[触ってみる](https://chairside.loncoeng.workers.dev)** — 右上の「デモ」を押すと、
ブラウザの中だけで動きます。予約を入れても他の人には影響しません。

---

## なぜ汎用の予約システムにしなかったか

GitHub で `appointment-booking` は652件、`reservation-system` は762件あります。
上位はどれも何年もかけて育ったものです。ここから汎用品を作っても、劣化版が
1つ増えるだけでしょう。

1軒に絞ると、汎用品には書けないことが書けます。**「この機能は作らなかった。
理由はこれ」と言えること**です。その一覧は [DESIGN.ja.md](DESIGN.ja.md) に
あります。このリポジトリで読む価値があるのは、たぶんそちらです。

## スキーマの決め手

最初にやったのは、店の中を数えることでした。セット面9台、シャンプー台3台、
スタイリスト8人。**種類によって足りなくなるタイミングが違う**ので、まとめて
「席」とは呼んでいません。

| | 台数 | |
|---|---|---|
| セット面 | 9 | スタイリスト8人に対して1台多いだけ。カラーの放置中は1人で2台使う |
| シャンプー台 | 3 | 稼働率は1日平均47%。ただし夕方に集中する |

### 断るものと、知らせるだけのもの

同じスタイリストが同じ時間に2か所にいる予約は受け付けません。物理的にあり
得ないからです。

一方、セット面が10台目になる・シャンプーが4件重なるといった場合は、警告を
出したうえで通します。**予約はお客様を待たせながら入力するもの**で、そこで
突っぱねるシステムは現場で使われなくなります。その日の店の状況は、受付に
立っている人のほうがよく知っています。

### 辞めたスタッフは消さない

削除すると過去の予約から担当者が消え、スタイリスト別の売上が合わなくなり
ます。退職は `left_on` に日付を入れるだけです。退職を登録すると、その人に
入っている先の予約が一覧で出ます。引き継ぎ先は店が決めることなので、自動で
は振り替えません。

### 為替レートは店が決める

マカオの美容室はほぼ 1:1:1 で、たまに 1:1.03 を見かけます。相場ではなく
店の方針なので、外部のAPIを叩く必要がありません。会計ごとにその時点の
レートを控えているため、後から方針を変えても過去の売上は動きません。

## 1つのスキーマで、3つの環境

D1 の実体は SQLite です。スキーマもクエリもそのまま使い回せます。

| 環境 | 用途 | ドライバ |
|---|---|---|
| Cloudflare Workers + D1 | 店の本番 | `drizzle-orm/d1` |
| Node + SQLite ファイル | PC1台で完結させたい場合 | `drizzle-orm/better-sqlite3` |
| ブラウザ内 SQLite (WASM) | 公開デモ | `drizzle-orm/sql-js` |

D1 を名指ししているのは [`src/worker/index.ts`](src/worker/index.ts) の20行
だけです。残りはすべて drizzle の SQLite 基底型に対して書いてあります。

この手の「どこでも動きます」は、放っておくと嘘になります。誰かが D1 固有の
機能を使っても本番は動き続け、README の一文だけが取り残されるからです。
そのため [`src/db/portable.test.ts`](src/db/portable.test.ts) で、**本物の
クエリ関数を sql.js の上で走らせて**います。

おかげでデモは、本番と同じコードに別のデータベースを渡しているだけです。
別実装にすると必ずずれますし、ずれたデモは無いほうがましです。

## 開発環境

```sh
npm install
npm run dev
```

`npm run dev` は画面だけを立ち上げます。API は Worker 側にあるので、両方
動かすなら `npx wrangler dev` を使ってください。DBはローカルの写しを見ます。

## サインイン

店で働く人はそれぞれログインを持ちます。サインイン画面と `/api/version` の
2つを除けば、ログインなしで答えるものはありません。売上と設定はオーナー
だけで、スタイリストには出しません。

セッションは署名つきトークンを HttpOnly の Cookie に入れて持ち回ります。
有効12時間で、リクエストごとにDBは引きません。パスワードは PBKDF2-SHA256
を10万回、1人ずつ別のソルトで。

Worker に署名鍵を入れるまで、誰もサインインできません。

```sh
npx wrangler secret put SESSION_SECRET
```

鍵が無いあいだ、サインインはすべて 503 を返します。これはわざとです。鍵が
無いときに素通しさせる作りは、鍵の無いまま本番に出ます。

## 個人情報の扱い

顧客の氏名・連絡先・施術履歴を扱います。マカオの個人資料保護法（Lei n.º
8/2005）は EU の枠組みを踏襲しており、個人資料保護辦公室への届出は店側の
義務です。このソフトウェアが代行するものではありません。

**実データはリポジトリに入れません。** 入っているのはコードとスキーマ、
そして完全に架空のサンプルだけです。CI では `publish-guard verify` を
git の履歴ごと走らせ、氏名や住所が紛れ込んでいないか確認しています。

禁止語のリストは設定ファイルではなく GitHub Secret から渡しています。
**隠したい語を、隠すための設定ファイルに書いてしまっては本末転倒**だから
です。
