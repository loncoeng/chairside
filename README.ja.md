# chairside

*[English version](README.md)*

マカオの美容室1軒のための予約・顧客管理です。セット面9台、シャンプー台3台、
通貨は MOP・HKD・CNY の3つ。

置き換える相手は、マクロを少し足した Excel です。

[**触ってみる**](https://chairside.loncoeng.workers.dev) — 最初の画面の
「デモを開く」を押すと、ブラウザの中だけで動きます。何をしても他の人には
見えませんし、再読み込みで元どおりです。

## なぜ汎用の予約システムにしなかったか

GitHub で `appointment-booking` を検索すると652件、`reservation-system` は
762件。上位はどれも何年もかけて育ったものです。今から汎用品を作っても、
劣化版が1つ増えるだけでしょう。

1軒に絞ると、汎用品には書けないことが書けます。「この機能は作らなかった、
理由はこれ」という話です。一覧は [DESIGN.ja.md](DESIGN.ja.md) にまとめました。
読む価値があるのは、たぶんそちらです。

## スキーマの決め手

最初にやったのは、店の中を数えることでした。セット面9台、シャンプー台3台、
スタイリスト8人。足りなくなるタイミングが種類ごとに違うので、まとめて「席」
とは呼んでいません。

| | 台数 | |
|---|---|---|
| セット面 | 9 | スタイリスト8人に対して1台だけ多い。カラーの放置中は1人で2台使う |
| シャンプー台 | 3 | 1日平均の稼働率は47%。ただし夕方に集中する |

### 断るものと、知らせるだけのもの

同じスタイリストを同じ時間に2か所へ入れる予約は受け付けません。物理的に
あり得ないので。

セット面が10台目になる、シャンプーが4件重なる。こういうときは警告だけ出して
通します。予約はお客様を待たせながら入力するものなので、ここで突っぱねると
現場で使われなくなります。その日の店の様子は、受付に立っている人のほうが
よく分かっています。

### 辞めたスタッフは消さない

消すと過去の予約から担当者がいなくなり、スタイリスト別の売上が合わなく
なります。退職は `left_on` に日付を入れるだけ。登録すると、その人に入って
いる先の予約が一覧で出ます。引き継ぎ先は店が決めることなので、自動では
振り替えません。

### 為替レートは店が決める

マカオの美容室はほぼ 1:1:1 で、たまに 1:1.03 を見かけます。相場ではなく店の
方針なので、外部のAPIは要りません。会計のたびにその時点のレートを控えて
いるので、後から方針を変えても過去の売上は動きません。

## 1つのスキーマで、3つの環境

D1 の実体は SQLite です。スキーマもクエリもそのまま使い回せます。

| 環境 | 用途 | ドライバ |
|---|---|---|
| Cloudflare Workers + D1 | 店の本番 | `drizzle-orm/d1` |
| Node + SQLite ファイル | PC1台で完結させたい場合 | `drizzle-orm/better-sqlite3` |
| ブラウザ内 SQLite (WASM) | 公開デモ | `drizzle-orm/sql-js` |

D1 を名指ししているのは [`src/worker/index.ts`](src/worker/index.ts) の20行
だけ。残りは drizzle の SQLite 基底型に対して書いてあります。

ただ、この手の「どこでも動きます」は放っておくと嘘になります。誰かが D1 固有
の機能を使っても本番は動き続けるので、README の一文だけが取り残される。
そこで [`src/db/portable.test.ts`](src/db/portable.test.ts) が、本物のクエリ
関数を sql.js の上で走らせています。

おかげでデモは、本番と同じコードに別のデータベースを渡しているだけで
済んでいます。

## 段階を分けて作った

1段階ごとに必ずデプロイしました。最後にまとめて公開する作り方だと、途中で
行き詰まったときに何も残りません。

- [x] 1 — 骨組み。公開するところまで通す。DBはまだ繋がない
- [x] 2 — D1 とスキーマ。画面がDBから読むところまで
- [x] 3a — カレンダー。列が席、行が15分の格子で1日を表示
- [x] 3b — 予約を取る。あり得ないものだけ断り、残りは警告して通す
- [x] 3c — 予約を変える。状態・時間・担当。削除は作らない
- [x] 4 — 顧客とカルテ。来店履歴から見えてくるもの
- [x] 5 — 会計と売上。会計はボタン1つ、集計は月単位
- [x] 6 — 祝日・営業時間・スタッフ。マカオ/香港/中国の3地域ぶん
- [x] 7 — 公開デモ。同じコードを、ブラウザ内の SQLite で

## 開発環境

```sh
npm install
npm run dev
```

`npm run dev` は画面だけ立ち上がります。API は Worker 側なので、両方動かす
なら `npx wrangler dev` を使ってください。DBはローカルの写しを見ます。

## デモと、店のインスタンス

上のURLはデモです。「デモを開く」を押すと、店ひとつぶんがブラウザの中に
降りてきます。WebAssembly の SQLite と、架空の店の5週間ぶんのデータ、それに
Worker が動かしているのと同じルータ。どこにも送信されませんし、再読み込みで
元に戻ります。

データは開いた日に合わせて前へずらしています。ずらす幅は週単位です
（月曜が定休なので、半端にずらすと火曜ぶんの予約が休みの日に乗ってしまう）。

その下にあるのが店の人用のサインインですが、ここは誰も開けません。アカウント
はデモ側のDBにあって、公開インスタンスには置いていないからです。訪問者が
書いたものを次の訪問者が読む、ということが起きません。実際に使う店には、
その店の Worker とDBとパスワードを用意します。

## サインイン

店で働く人はそれぞれログインを持ちます。サインイン画面と `/api/version` を
除けば、ログインなしで答えるものはありません。売上と設定はオーナーだけで、
スタイリストには出しません。

セッションは署名つきトークンを HttpOnly の Cookie で持ち回ります。有効12時間、
リクエストごとにDBは引きません。パスワードは PBKDF2-SHA256 を10万回、1人ずつ
別のソルトで。

署名鍵を入れるまでは誰もサインインできません。

```sh
npx wrangler secret put SESSION_SECRET
```

鍵が無いあいだ、サインインは全部 503 です。わざとそうしています。鍵が無い
ときに素通しさせる作りだと、鍵を入れ忘れたまま公開してしまうので。

## 個人情報の扱い

顧客の氏名・連絡先・施術履歴を扱います。マカオの個人資料保護法（Lei n.º
8/2005）は EU の枠組みを踏襲していて、個人資料保護辦公室への届出は店側の
義務です。このソフトが代わりにやってくれるものではありません。

実データはリポジトリに入れていません。入っているのはコードとスキーマ、それに
完全に架空のサンプルだけです。CI で `publish-guard verify` を git の履歴ごと
走らせ、氏名や住所が紛れ込んでいないか見ています。

禁止語のリストは設定ファイルではなく GitHub Secret から渡しています。隠したい
語を、隠すための設定ファイルに書いてしまっては元も子もないので。
